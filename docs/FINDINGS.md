# Findings log, in the order they were made

*Moved from AGENTS.md on 2026-11-12. One entry per stage or test, with the numbers and where the rows are. The story in order is in the [README](../README.md); this is the dense version.*

Summary with figures: `README.md`; details per stage in the linked docs.
- **Phases 1-2 (K1-K3): KILL.** Substitution saves only ~1.19x em (K1); PP-OCR zero-shot misses the K2 bar (0.89x); trained CRNNs: plain Latin wins (1.73% CER at 7.5 px²/char vs subst300 2.26% at 8.9); px²/char needed for 3% CER: Latin 6.54, subst300 8.20 (1.25x), subst1000 9.66 (1.48x), from the regenerated merge of 2026-11-13. Claude reads natural Latin at 29.4 px²/char for 3% CER and cannot be used on codes. `docs/glyphs/RESULTS.md`.
- **Learned glyph alphabet: qualified GO for raw pixels.** Learned N=300 needs 0.57x Latin's px²/char at 3% CER (bridge), 0.88x for whole-pixel banks; the densest banks are brittle on held-out degradations. `docs/glyphs/RESULTS.md`, `learned_glyphs/RESULTS.md`.
- **Frozen encoders (rounds 1-2, SigLIP, DeepEncoder): dense codes are lost.** Colour/RGB codes are dead; grey-level banks are not supported; only low-density Latin is readable through the encoder. Learned glyphs should be whole-pixel. `encoder_probe/RESULTS.md`.
- **Round 3 (Qwen2.5-VL-3B), CPU:** the moonshot `rgb3_lg_pb_h5` (322 chars/token) is readable from raw pixels (G0 1.07% CER); glyph codes stay pixel-like through the ViT but collapse at the merger (Q1); G2-lite: no arm usable. `encoder_probe/ROUND3.md`.
- **Round 3 R3-1 (RTX 4090, 1000 steps, blind controls): only latin_p8 (28 chars/token) is read** (55% CER vs blind 88.5%; it reads the first line, then drifts). latin_p5 (72) gets the gist only (val loss 9.9% below blind, MC p = 0.02); lg_pb_h5 (107; blind died at step 500) and the moonshot are not read (losses = blind's). **G3 is undecidable** (no arm near 3% CER). `docs/background/history/HANDOFF_2026-11-12.md`.
- **Analysis (`docs/background/ANALYSIS.md`, `analyse_r3.py`):** Q1, G2-lite and R3-1 all put the glyph codes' loss inside the frozen ViT, upstream of R3-1's 4 trained blocks; the moonshot needs ~270 bits per vision token beyond the language prior vs 12.7 delivered by latin_p8.
- **Own encoder Stage 0 (RTX 4090):** inconclusive; the 4x control reached 64% CER at 8000 steps (gist, not copying), ~8 bits per slot at both ratios. `docs/gpu/OWN_ENCODER.md`.
- **Colour gist (2026-11-06, the user's current direction, `docs/gpu/COLOUR_GIST.md`):** Latin in 2-3 colour channels, gist as the target. Untrained Qwen reads the overlay as one blended text (R(2) = 0.51 at 16 px); A1-cpu (LoRA only, ViT frozen, 500 steps) R(2) = 0.72 (0.54-0.94), missing the > 1 headline; both streams survive equally in the frozen ViT to block 16, then blend (not a brightness effect: balanced inks flip which stream wins). S1 (small VLM, encoder from scratch, CPU): closed inconclusive, the 1-stream control never became readable (gap ≤ 0.001 in 3 runs).
- **Run 0 (2026-11-07, CPU, `docs/gpu/PLAN_3090.md` Results):** frozen Qwen2.5-VL-3B recovers at most 12.6 bits per vision token on natural text (25.7 on word-shuffled) at latin_p8 (28 chars/token), then collapses (latin_p5: 1.7). Three regimes PASS, shuffled < natural in preservation PASS (6/6 pitches), NLL-tracks-CER narrowly FAIL (ρ = -0.78 vs ≤ -0.8): zero-shot greedy transcription runs past the requested lines, so use the NLL gap for zero-shot points. Tool: `capacity_curve.py`. Run 0b (grid shifts 0-21 px): no zero-shot grid-phase effect; small (8 px) text flush with the page's top edge loses ~1.2 bits/token (~10%, dy = 28 control), so render with a top margin. Grid-aligned whole-pixel banks (7-px rows; chars 2x7/4x7/7x7, BPE 2x7+4x7) in `learned_glyphs/results/e1align/`: bridge CER 0.08/0.03/0.01/0.11% (BPE: 76 chars/token vs Latin 0.58% at the same px²/char). Amendment 4 CPU tasks: min-distance banks (`train_joint.py --min-dist-px 2`) `lg_n0_pb_c2_h7md` / `lg_pb_c2t4_h7md` have 0 identical glyphs (was 35 / 13), min 2 px apart, bridge CER 0.021% / 0.025% (was 0.083% / 0.110%), 53.4 / 74.3 chars/token with the 7-px margin. Run 0b at latin_p6 with margins on every shift: a real phase effect (perm p < 0.001, cross-validated 1.9 bits, CI 0.9-2.8), all vertical, period 28 px not 14, on-grid (28, 28) not better; zero-shot, dy = 21 beats the `--top-margin 7` placement by 1.3 bits/token.
- **Goals reframed (2026-11-11, `docs/background/REVIEW_2026-11-11.md`, the README of that date):** the idea began as braille-like glyphs readable at low resolution, with BPE chunks and the RGB overlay as extensions; it holds for raw pixels and fails at every pretrained reader. Now: (1) page images as cheaper context for Claude, stretched from the text side (Test A: prune, then render); (2) text slots against page pixels on a trainable model (Test B, `docs/gpu/TEXT_SLOTS.md`, 3090 prompt in `docs/HANDOFF.md`); (3) finish Stage A, channel capacity and Stage B of Runs 1-2 as the fair test of the original idea, with Stage C and colour Run 4 held until Test B is in.
- **Test A (2026-11-12, Opus 5.5 high effort, 480 paired questions, `results/claude_qa/prune/README.md`): pruning the text neither replaces pages nor stacks with them.** Pruned text matched to the 2.2x pages' tokens: 86.0% (original 120: 96.4%; small-word: 55.0%) vs pages 97.7% and text 100%; lightly pruned (1.5x) text as pages (3.4x): 90.6%, the same as pages alone at 4.1x and below pages at 2.85x (99.0%). LLMLingua-2 drops "not", "all but" and "was ... by", and Claude then answers with the sentence's other number. Open: the 2.2x pages lost nothing on the original 120 but scored 90.8% on small-word questions (every passive wrong in 2 of 3 calls; 2.9x pages 98.3%): answers of one type are correlated within a call, so repeat calls before reading it as a density effect.
- **Repeat calls (2026-11-12, Opus 5.5 high effort, 27 calls, $16.17, `results/claude_qa/repeat/README.md`): pages lose about 3 points on wording-sensitive questions at 2.2x and 2.85x alike** (97.2% and 96.2% vs text 100%; intervals over whole calls exclude 0), and the original 120 questions stay within 0.7 points. Test A's "2.2x flips the passives" was call-to-call variation: 5 of 30 page calls (2 at 117.6, 3 at 88.2) answer all five passive questions with the lure, 0 of 6 text calls; it is all or nothing per call and not explained by page layout. Repeats need `claude_eval.transcribe(..., cache_salt=...)`, or the cache returns the first answer.
- **Repo atlas pilot (2026-11-12, Opus 5.5 high effort, 8 SWE-bench tasks in requests / gin / bat / preact, 36 calls, $7.49, `results/atlas/pilot/README.md`): cannot separate the arms.** Every arm, including the file list alone (~2k tokens), named every changed source file; with only the file list the model described the real fixes, so these public tasks are memorised or the issue gives the location away. Claude Code with read-only tools found the files in ~3 turns for $0.04 per task; the atlas cost $0.23 (45k image tokens), the same code as text $1.18. A localisation test needs tasks the file-list arm misses (screen at $0.015 per task) or issues newer than the model; the full stage 1 was not run.
- **Repo atlas vs SWE-QA (2026-11-12, Opus 5.5 high effort, 144 questions on requests / flask / pytest, $20.83, `results/atlas/qa/README.md`): the atlas does not help on code the model already knows.** Judge score (5-100): no code 75.6, repo map 76.1, atlas 75.4, text 75.5 (96 questions); only Claude Code searching the checkout beats memory (79.1 on 72 questions; +3.3 over the atlas, interval 2.3-4.4). With no code the model already names 71% of the code entities in the reference answers. In `claude -p` a context is read from the prompt cache only when it is its own first user message, separate from the questions. Tests of the atlas need code from after the model's training data (done later the same day: the fresh-task, migration and security tests below).
- **Repo atlas vs security flaws (2026-11-12, Opus 5.5 high effort, 12 advisories published 2026-11-09..11 with fixes after 2026-07-01, in small libraries, $20.70, `results/atlas/sec/README.md`): the atlas alone does not help find the flaw; with an agent it may.** A gold file in the top 5 findings: file list only 10 of 12, atlas one-shot 9, Claude Code with read-only tools 7, the same agent with the atlas up front 10 (3 tasks to 0 against the plain agent, exact p = 0.25) in a median of 8 turns instead of 18, at $0.67 vs $0.46 per task. File names give the location away even for post-cutoff flaws (`security.ts`, `ZipUtil.java`), so the primary score is near its ceiling. VulnGym (the existing repository-level benchmark) cannot be used: its smallest measured repository is 246k image tokens. `repo_atlas.collect` leaves out files that contain its marker characters (`§`, `▶`).
- **Repo atlas on hard coding tasks (2026-11-12, Opus 5.5 high effort, 16 SWE-rebench tasks with 3+ files in the fix, $28.45, `results/atlas/swe/README.md`): atlas 11 solved, repo map 9, plain 8.** All 3 discordant tasks favour the atlas (exact p = 0.25, one run per task: not settled); the atlas uses fewer turns (median 10 vs 12.5, sign test p = 0.006) and costs 2.6x ($0.68 vs $0.26 per task). SWE-rebench and SWE-bench-Live hold nothing newer than 2026-05, so a closed-book screen (file list only) dropped 12 of 37 candidates as memorised or trivially located. One run leaked the fix by downloading a later PyPI release of the package: block the package index for agents (amendment 1). A background job in an agent run produces several result events: sum turns and tokens over all of them.
- **Repo atlas on C-to-Rust migration (2026-11-12, Opus 5.5 high effort, 14 CRUST-Bench projects x 3 arms, $24.01, `results/atlas/migrate/README.md`): no effect.** Claude Code with the C files, with files and atlas, and with the atlas only (no C files) tie on every project (12 of 14 pass all tests in each arm; turns and cost equal within noise). Projects are small (atlases 2-13k image tokens), public since 2025, and the Rust interfaces and tests carry much of the behaviour. **Claude Code's auto-memory (`~/.claude/projects/`) is shared across headless runs: one run read another's notes; turn it off or delete each run's store.** Grade each cargo test binary separately with its own timeout (one slow test hid the others), and key tests by binary.
- **Hard coding tasks again, auto-memory off (2026-11-12, Q1, 64 runs, $35.07, `results/atlas/swe_rerun/README.md`): the atlas hint does not survive.** Task-runs solved of 32: plain 19, atlas 17 (run 1: 10 vs 9; run 2: 9 vs 8; atlas higher on 1 task, plain on 2); turns lower with the atlas on 10 of 15 untied tasks (p = 0.30); cost 3.1x ($0.83 vs $0.27 per run). The first test's transcripts show each run had its own memory store and none was written, so its 11 vs 8 and "fewer turns" (p = 0.006) were run-to-run variation: plain alone moved from 8 to 10. One run per task cannot carry a 3-task difference on 16 tasks; the security hint (3 to 0 on 12 tasks) is unrepeated and should be read the same way. A subagent stopped by a session restart cannot be resumed: have long runners write rows the main session can analyse.
- **Repo atlas on a larger port (2026-11-12, Q2, RepoMod-Bench gitleaks Go to Rust, 22k lines, one run per arm, $23.14, `results/atlas/port/README.md`): no effect.** Plain and atlas both build and pass 35 of 35 hidden tests in ~40 min, 102 vs 99 turns, $11.32 vs $11.20; neither port scans concurrently (the Go original does; the tests do not check). Both agents built the Go original and diffed outputs against it. **The CLI prices Opus cache reads at $0.20/M (0.05x input), not $0.40/M**: a live cost guard using 0.1x ran 40% high and cut both runs early (resumed with `claude -p --resume`). `assistant` stream events carry only a message's starting output count: use `--include-partial-messages` and read `message_delta`. Docker has no daemon here; the benchmark's pytest suite runs directly with `--work-dir` / `--run-cmd`.
- **Sonnet with the atlas (2026-11-12, Q3, Sonnet 5.5 high effort, the same 16 tasks x 2 runs, $11.38, `results/atlas/swe_sonnet/README.md`): no effect.** Sonnet reads the atlas as well as Opus (20 of 20 lookups each; 1932-px pages are not downscaled for Sonnet), but solves 14 of 32 task-runs plain and 13 with the atlas (15 tasks tie) at 3.7x the cost ($0.26 vs $0.07); turns lean lower (11 of 14 tasks, p = 0.057). Opus with a brief solved 11 (atlas brief) or 10 (file-list brief) against 8 with none (3 to 0, p = 0.25, one run each): if real, the gain is from planning, not the atlas.
