# Go-forward plan: glyphs through a trained encoder (3090), reviewed 2026-11-06

Source: the user's "Visual BPE: Prior Work and 3090 Research Plan" (6 Nov 2026). This file is that plan after review,
with the corrections and the CPU work that can run before any GPU time. It supersedes the colour-first order in
`COLOUR_GIST.md` and `HANDOFF.md` (that GPU A1 prompt is parked; its colour arm returns as Run 4).

## The claim and the metric (adopted unchanged)
* **Claim:** a frozen or lightly fine-tuned LLM reads dense glyphs through a trained encoder at well over the ~28
  chars per vision token of plain rendered Latin.
* **Metric:** bits recovered per vision token = teacher-forced NLL of the source text without the page minus with
  the page, on two text sets:
  * natural prose;
  * block-shuffled text, which removes the language prior (ZeroSense: DeepSeek-OCR 95.4% on natural FOX text
    but 11.8% preservation on low-predictability text at 10x).
* **QA (needle, cloze) runs once,** on the winner.
* **What the repo already measures:** `zeroshot_info.py` and `analyse_r3.py` compute the same quantity, so the
  metric is not new code, only a new text set.

## Review: what holds, what to correct

**Holds (keep):**
* The encoder must train. Our own results agree: rounds 1-3 lost dense codes inside frozen encoders, and Q1 /
  G2-lite / R3-1 put the loss inside Qwen's ViT.
* Matched-density Latin controls, a blind control per arm, a text-budget baseline, CIs, a 500-step smoke before
  any overnight run, and gates.
* Stopping S1. Done: closed inconclusive at 21:05 UTC (`COLOUR_GIST.md`, "S1 result").

**Citations checked** (arXiv abstracts or HTML opened 2026-11-06):
* **2608.01848 (ZeroSense):** correct. The 95.4% / 11.8% figures are on different datasets (FOX vs ZeroSense),
  both at 10x.
* **2512.03643 (Bad Autoencoding):** correct.
* **2611.01517 (VLMs Read Aloud):** correct (15 px recognition vs 24 px use, Qwen3-VL-8B).
* **2601.10378 (VIST2):** the 0.912 is real (VIST2-8B, r = 16, Table 2, "ROUGE", stage-2 OCR), but the paper's
  main experiments use r = 4. Treat "a trained encoder reaches ~16x" as an OCR-reconstruction number, not a usage
  number.
* **2602.02539 (vision-token capacity):** the paper and its three regimes are real. Two claims are unverified:
  * the abstract names no models, and "Qwen2.5-VL-8B" does not exist (Qwen2.5-VL is 3B/7B/32B/72B);
  * arXiv links no code, so check the renderer, harness and pixel-shift repo exists before planning around it.
    Run 0b below does not depend on it.

**Corrections:**
1. **"The earlier 0.72x (CI 0.54-0.94) was unreadable because the CI crossed the decision line": not so.** The
   whole CI is below 1, a clear miss of the > 1 bar. What limited A1-cpu was the setup: ViT frozen, 500 steps, 64
   val samples, a conservative blind. The ±0.1 CI target is right.
2. **Run 4's two-frame multiplex does not work on Qwen's pretrained patch embedding.**
   * Measured from the weights: the two temporal kernel slices of `visual.patch_embed.proj` (1280 x 3 x 2 x 14 x 14)
     have cosine 0.999 per output channel, and ||f0 - f1|| / ||f0 + f1|| = 0.026. Two different frames are
     *summed* at the first layer; only ~3% of the kernel sees their difference.
   * The RGB channel kernels are far more distinct: cosine R-G 0.38, G-B 0.32, R-B 0.13. The colour directions are
     luminance 53%, R−B 28%, G−(R+B) 19%.
   * So colour multiplexes better than frames. Run 4 becomes colour, with the R/B ink pair as the most separable at
     the conv. Frames are tested only with the patch embedding trainable (Run 4b, optional).
3. **The glyph density range.** Measured at 448 px:

   | Encoding | chars per token |
   |---|---|
   | latin_p16 | 6.8 |
   | latin_p12 | 12.2 |
   | latin_p10 | 17.6 |
   | latin_p8 | 28.2 |
   | latin_p6 | 50.1 |
   | latin_p5 | 72.6 |
   | lg_n0_pb_h5 (characters-only glyphs, 95 symbols) | 76.8 |
   | lg_pb_h5 (glyph per BPE token, N = 300) | 107 |
   | lg_pb_h4 | 135 |
   | moonshot (colour + BPE) | 322 |

   * Without BPE or colour, glyphs are no denser than Latin at the same height (77 vs 73). They can only win on
     **legibility at matched density**, which is exactly Run 2's pass test.
   * To sweep below 77, upscale the whole-pixel bank by integer factors: x2 ≈ 19 chars/token (matches latin_p10),
     x3 ≈ 9. The alphabet stays the same and no new bank training is needed.
   * Above 77 needs BPE banks (107-135) or colour; 300 is not reachable without colour.
4. **"A glyph set learned for the encoder" is not what Run 2 tests.** The existing banks were learned for a CRNN
   reading raw pixels. Run 2 asks whether a trained ViT can read *those*. The claim nobody owns needs the bank
   trained through Qwen's ViT (differentiable rendering into the patch embedding), added as Run 2c. That is the
   contribution run, and it goes after Run 2 so it has a baseline.
5. **Blind control rule.** "Blind NLL must equal the no-page baseline" is too strict: a swapped page legitimately
   differs from a blank one (format, topic). Use reference = min(swapped, blank) per sample, the repo's
   conservative blind. Treat a blind *below* that reference as a leak.
6. **Setup:**
   * **WSL2 is optional.** The native-Windows runbook (`docs/LOCAL_GPU.md`) already ran round 2 on this 3090,
     SDPA needs no flash-attn, and switching costs an evening. Switch only if something needs Triton.
   * **Keep WikiText-103** (built, tested, deterministic splits) instead of Gutenberg; block-shuffle it.
7. **Throughput:** measured R3-1 on an RTX 4090 was 1.2 s/step at batch 4 (3.3 pages/s, 4 ViT blocks + LoRA). A
   3090 is ~0.6x, and 16 trainable blocks cost more, so plan on ~1.5-2 pages/s: 50k pages ≈ 7-9 h. The plan's
   estimate is within its own 2x tolerance.

## Amendment 1 (2026-11-06): second external review, checked against the repo
A second LLM review proposed four fixes. Each was checked against measurements here before it changed the plan.
* **Fix 1, "unfreeze the whole ViT incl. patch_embed; little VRAM": partly adopted.**
  * Our own measurements say the early blocks do not discard the codes:
    * Q1: glyph codes stay pixel-decodable through Qwen's ViT and collapse at the merger;
    * colour: both streams survive equally to block 16;
    * Latin stops being pixel-decodable after block 24.
    So blocks 16-31 + merger stay the default for Runs 1-2.
  * The VRAM claim is wrong: the ViT is ~670M params, and AdamW with fp32 states needs ~16 bytes/param, so ~10.7 GB
    for the full ViT vs ~5 GB for blocks 16-31.
  * Added: one **full-ViT arm** (patch embed + all blocks, LR ≤ 2e-5, 8-bit Adam if VRAM needs it) at Run 2's best
    density. It is **mandatory for Run 4b (frames)**: the patch embed must learn to separate the two frames.
* **Fix 2, "Run 2b is a reviewer trap": adopted.** Run 2b is a diagnostic ablation (is the pretrained ViT the
  bottleneck?), never the recipe. The claim has to hold through the VLM's native vision tower.
* **Fix 3, "glyph cells must divide 28": adopted, as a test rather than an assumption.**
  * The banks' measured cells are 2 x 5 px (characters) and 4 x 5 px (BPE tokens). Rows of 5 px straddle every
    14-px patch and 28-px token boundary.
  * A cell that divides 28 but not 14 (e.g. 4 px) still straddles the 14-px patch boundary, so the review's 4 x 4
    example is not clean. Clean heights: 7 or 14 px; clean widths: 2, 7 or 14 px.
  * New CPU work: train aligned banks with the learned_glyphs joint trainer (≥ 10.5k steps, CPU):
    * characters 2 x 7 px = **56 chars/token**, fully aligned (a latin_p6-like density);
    * BPE 4 x 7 px.
  * Run 2 then compares aligned vs the current 5-px banks at matched density.
  * Run 0b measures the Latin phase sensitivity zero-shot.
* **Fix 4, "mix QA into the Run 3 LoRA": adopted.** 15-20% cloze / needle / span-extraction samples (the repo's
  `r3_tasks` already generates cloze and MC). The capacity metric stays pure-transcription NLL on fixed val pages,
  and Run 5 uses disjoint text and formats.
* **Not adopted:**
  * **"Run 4 temporal multiplex is the secret weapon (65%)".** The pretrained patch embed sums the two frames
    (kernel cosine 0.999). Frames are only viable with the patch embed trained. In principle that is possible: a
    2-frame RGB patch is 1176 values into 1280 dims, so a trained first layer can carry both frames.
    * The repo's only multiplex evidence is negative so far: colour R(2) = 0.51 zero-shot and 0.72 with LoRA.
    * The gains do not multiply (1.75 x 2 x 3).
  * **The success probabilities:** no basis.
  * **"~1.3x for whole-pixel glyphs":** the repo's bridge number is 0.88x Latin's px²/char, i.e. ~1.14x density.
  * **"The CRNN ratio transfers to the VLM":** R3-1 read latin_p8 but not lg_pb_h5 (107 chars/token) with 4 trained
    blocks + LoRA, so transfer is the open question, not an expectation.

## Amendment 2 (2026-11-06, before any Run 0 / 0b row): how C1-C3 are run and judged
Written before the first Run 0 / 0b row existed; nothing below was chosen after seeing data.
* **Tool:** `encoder_probe/experiments/capacity_curve.py` (docstring = the full definition; tests
  `encoder_probe/tests/test_capacity_curve.py`, tiny model).
* **Shuffled text = word-level shuffle within the page's own passage** (fixed seed per page), not block shuffle:
  it keeps the page's vocabulary, letters and word lengths (same rendered density as natural), and removes syntax
  and most of the prior beyond the single word.
* **Window:** each page scores one window of whole lines from the top of the page, at most 2000 target chars
  (the whole page for latin_p16), with the "Transcribe lines a-b of the n lines" prompt. The page's information
  is extrapolated per char (x page chars / window chars). The top window may read better than the page average,
  so the densest points are upper bounds in that respect.
* **Arms:** real, swap (page i+1), blank (white). Reference = per-sample min(swap, blank).
* **CER:** greedy transcription of the window on the first 3 pages per point. It is only a coarse check (3 pages).
* **Pages:** 32 per point. If the measured cost of the 12 points exceeds ~4 h, 16, and the Results say so.
* **Run 0 criteria, made operational:**
  * **Three-regime curve** (natural text, 6 pitches). Pass needs all three regimes:
    * near-lossless: recovered fraction ≥ 0.8 at the sparsest pitch(es);
    * a middle range where the recovered fraction falls but bits per vision token still rises;
    * a top range where bits per vision token falls as density rises: an interior maximum, with the densest
      point's CI upper bound below the maximum's mean.
  * **NLL gap tracks CER:** Spearman ρ between gap per text token and CER over the points with CER is ≤ -0.8.
  * **Shuffled < natural.** Read as *preservation*, the source plan's ZeroSense sense: the recovered fraction (and
    CER where measured) on shuffled text is worse than on natural text at matched pitch, at ≥ 4 of 6 pitches.
    Raw bits per vision token are expected to be *higher* on shuffled text wherever the page is legible: the
    image must supply the bits the prior no longer does. So bits are reported, but they are not the test.
* **Run 0b:**
  * The text is rendered once at 448 - 21 = 427 px and pasted at (dx, dy) ∈ {0, 7, 14, 21}² on a white 448-px
    page, so every shift has the same text and none is cut. This gives slightly fewer chars per page than Run 0.
  * Arms: real at the 16 shifts, plus the blank page (identical across shifts, scored once per page). Only the
    real arm differs between shifts, so the comparison is exactly paired.
  * Pre-registered test (unchanged): best minus worst shift, page-bootstrap CI, best and worst re-selected inside
    each replicate. That CI is biased away from 0 by the selection itself, so three unbiased checks are reported
    next to it:
    * a within-page permutation p for the max-min spread;
    * a cross-validated best-vs-worst (chosen on half the pages, measured on the other half);
    * aligned (0, 0) minus the mean of the other shifts.
  * The verdict states all four. "Reliable" also needs the permutation p < 0.05.
* **Aligned banks (Amendment 1, Fix 3):** the joint trainer already has `--char-w` / `--token-w` / `--height-px`.
  Whole-pixel 2 x 7 (characters, N = 0) and 2 x 7 + 4 x 7 (N = 300) banks: `--pixel-block --guard-ss 0
  --height-px 7`, 10.5k steps, run `e1align`.

## Amendment 2 (2026-11-06): colour layers carry consecutive text (user memo), checked
The user's memo: pack text sequentially so each 28-px token holds one contiguous run of text, with the colour layers
(R, then G, then B) carrying consecutive pieces of it. Overlay stops being its own run and becomes a within-cell
layout option in Run 2, compared at matched chars per token. **Adopted, with three corrections to its reasoning:**
1. **The premise.** The A1 streams were already consecutive text, at *page* granularity.
   * In `rgb{k}s`, stream 2 continues where stream 1's page ends (`SizedStreams.render`). Only A0 used unrelated
     passages.
   * The real change is granularity: token-level contiguity instead of page-sized spans.
2. **"It explains the block-16 collapse / nothing to demix": not supported.**
   * Q1 measured both streams equally decodable to ViT block 16, then blending inside the ViT.
   * With sequential packing the layers still overlap at the same pixels, so the ViT still has to separate
     superposed strokes.
   * What sequential packing removes is the LLM-side bookkeeping: one reading order, a contiguous target per token,
     monotone attention. It may help the LLM and from-scratch training. The ViT-side fix is still training the ViT
     (blocks ≥ 16).
3. **"The patch embedding's RGB weights are close to luminance": not so.**
   * Measured: channel-kernel cosines R-G 0.38, G-B 0.32, R-B 0.13. The luminance direction carries 53% of the
     energy, R−B 28%, G−(R+B) 19%.
   * The near-identical kernels are the two *frames* (cosine 0.999). So a trainable patch embed is required for
     frames, not for colour. The colour arms run on the default recipe, plus the full-ViT arm from amendment 1.
   * With 3 binary ink layers all three channels are used. With 2, use R and B (the most distinct pair).

**Layout arms for Run 2 (replace Run 4).**
* **Tiled layout:** each 28-px token is a self-contained block of glyph cells, read row by row inside the token, then
  layer by layer. Tokens are read in raster order. Characters per token are fixed by the cell geometry: (28/h)(28/w)
  cells per layer. Grid-aligned cells only (heights 7 or 14, widths 2, 4, 7 or 14 px).
* Characters-only alphabet first. Matched-density pairs:

  | Single layer | chars/token | 3 colour layers | chars/token |
  |---|---|---|---|
  | 2 x 7 cells | 56 | 7 x 7 cells | 48 |
  | 2 x 5 cells (current bank, untiled) | ~77 | 4 x 7 cells | 84 |

  The colour hypothesis is that 3 layers of *larger* glyphs beat 1 layer of smaller glyphs at the same density.
* **Frames** (2 frames x the same tiling): only in the full-ViT arm.
* **Combinations** only if both colour and frames win.
* **Plain Latin cannot be tiled legibly into 28-px blocks at these densities.** Latin stays the untiled reference
  curve (Run 0/1).
* **Dropped:** the stacked-overlay arms and the "2 streams > 1 stream at the same font" headline. The
  matched-density comparison replaces it (it was already the stricter, equal-density bar).
* **New bank needed:** characters-only 4 x 7 and 7 x 7 cells (CPU, learned_glyphs trainer), in addition to the 2 x 7
  bank from amendment 1.
