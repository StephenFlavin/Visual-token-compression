## The main point: which reader decides everything

**"Vision tokens are a hack" is right for open models and wrong for Claude.**

* **A closed model (Claude) has two input ports: text tokens and image patches.** A learned compressor produces
  vectors, and there is no way to hand Claude a vector except as an image. So the vision encoder is the only
  compressor a user can reach. It works because a 28-px patch carries ~7-9 legible characters while a text token
  carries ~2.9. It is a pretrained text compressor with pixels as its wire format, not an accident.
* **The same fact caps it.** Claude reads only what it was trained to read (natural text at ordinary sizes) and its
  classifiers refuse coded pages. Nothing learned about glyphs, colour or overlays on Qwen can be moved to Claude.
* **An open model can be trained, and then pixels do no work.** Rendering text you already have and training a
  vision tower to undo the rendering adds a lossy step. [OWN_ENCODER.md](../gpu/OWN_ENCODER.md) already says this ("once
  the encoder is ours, the pixels do no work"). Published comparisons agree ([prior-art.md](prior-art.md)): a learned
  text encoder reconstructs at perplexity 1.00-1.01 at 7.9-15.4x, the vision path 1.06-1.14 at 8.6-12.8x; C3 gets
  98% at 20x where DeepSeek-OCR gets ~60%.

So the dense-code line is squeezed from both sides: the reader that pays (Claude) cannot learn a code, and a reader
that can learn one is better served without pixels. It would matter only if the input is already an image (scans),
which is not this repo's case.

## Goals

* **Goal 3 (plain Latin pages, no training) is done and is the valuable part.** 2.2x lossless on Opus and Sonnet;
  the compaction archive (96-99% against 78% for normal compaction, 2.1x cheaper per correct answer) and RAG (+8.8
  points at the same budget) are the uses that pay. Coding agents do not pay: reading is 17% of their cost.
* **Goals 1-2 measure a pipe nobody needs to use.** They are clean science (bits per vision token through a trained
  ViT), and the runs are already queued, so finishing Stage A, the channel-capacity arms and Stage B costs only GPU
  time. Stage C and colour Run 4 should wait for test B.
* **The stated next goal, "raise chars per token to find the accuracy ceiling", is already answered for Claude**
  (the 2.2x / 2.9x / 4.2x sweep) **and is the wrong axis for Qwen**, where the competitor is a text compressor, not
  less-dense Latin.

## Methods

**What is sound:** predictions committed before the calls; a blind control for every trained arm; paired tests with
a stated margin; the engagement check; the check that every page arrived; cost from logged tokens.

**What limits the claims:**

1. **The Runs 1-2 bar uses the wrong baseline.** "> 20 chars recovered per vision token" compares glyphs with Latin
   pixels. A glyph arm can pass it and still lose to a text compressor at the same budget. Test B is that control.
2. **The text-side route was never fairly tested here.** Stage 0's 4x positive control failed (64.0% CER at 8000
   steps) and the line was parked. Its outputs were on-topic paraphrases with almost no exact prefix (0.3%): the
   recipe learned gist, not copying. That is a recipe failure (global memory slots, frozen decoder, ~15M training
   tokens against ~1B in the published comparison), not evidence about text compression.
3. **The Claude QA questions are lookups and chains over planted numbers.** Text scores 98-100%, so losses under
   ~1 point are invisible, and nothing tests wording that depends on small words (negation, passive voice, "at
   most"), tables, or other languages. This matters most for a pruned-text arm, which fails exactly there.
4. **One call per arm and document:** the intervals cover questions, not run-to-run variation. Repeating one arm
   three times would size it.
5. **Lossless is per model and per release.** Haiku fails at 2.2x and Sonnet only passes at high effort. A hook
   that ships this needs a short self-test (a page of planted facts) that it re-runs when the model changes.
6. **Local-model runs are short and single-seed** (1000 steps in R3-1). The docs say so; it means "not reached at
   this budget" for everything, including Latin.

## Can text compression beat images? Two tests (drafts for approval)

### Test A (Claude, no GPU, ~$10-15 at list price): prune, then render

A text-only arm for Claude has to be hard text: fewer real tokens. The repo already ran the abstractive version
(notes per source: 6x fewer tokens, -29 points; normal compaction: 37-78%). The extractive version at a matched
ratio is untested, and it stacks with pages because both are just text.

* **Compressor:** LLMLingua-2 (a 560M token classifier that deletes words the reader can restore), numbers always
  kept. Off the shelf first. Train one on the 3090 only if this shows promise: labels from a local LLM (a word is
  droppable if its removal does not raise the LLM's loss on restoring the sentence), no Claude calls.
* **Arms** (existing harness, same 3 documents and 120 questions, Opus 5.5 high effort, paired with the stored text
  rows): pruned text matched to the 2.2x pages' tokens; lightly pruned text (~1.5x) as text; the same ~1.5x text as
  117.6 px²/char pages (~3.3x total), compared with pages alone at 2.9x and 4.2x.
* **Add 40 questions per document that depend on small words** (who did what to whom, negations, bounds), so
  pruning is tested where it breaks. The text and page arms are re-run on them, which is most of the cost.
* **Predictions:** pruned text at 2.2x is not lossless (it loses on sentence-anchor and small-word questions);
  ~1.5x pruning under 2.2x pages is lossless on the current questions and beats pages alone at the same total.
  That is, text compression extends the pages rather than replacing them.
* **Risk:** Claude's classifiers refused scrambled English before. If pruned text is refused, that ends the arm; no
  rewording to get around it.

### Test B (3090): text-side slots against page pixels, same reader, same budget

The claim to test: with the same LLM (Qwen2.5-VL-3B's), the same steps and the same metric, m learned slots made
from the text tokens carry more per context position than m vision tokens made from a rendered page.

Changes to `text_compress.py` that address why Stage 0 failed:

1. **Local slots.** Slot i is built from its own r consecutive token embeddings (a position-weighted projection,
   mean-pool at initialisation) plus a small encoder. Copying becomes local unpacking instead of global routing. At
   r = 1 this is the LLM's own input, so the control is exact from step 0.
2. **Train the reader as the image arms did:** the same LoRA on the LLM as R3-1. A frozen-decoder arm stays as a
   second variant, with slots passed as key-value states per layer (500xCompressor) instead of one input vector.
3. **Ratio ladder with warm starts:** r = 1, 2, 4, 8, 16, each initialised from the last.

* **Gates:** r = 1 reads at ~0% CER at step 0 and r = 2 at ≤ 3% within 1000 steps, else it is a pipeline fault:
  stop. Every arm has its blind control (another window's slots).
* **Comparison:** bits per position on natural and shuffled text with `capacity_curve.py`'s measure, against frozen
  Latin (12.6 / 25.7 at 28 chars per token), R3-1's latin_p8 (55% CER, 12.7 bits) and whatever Runs 1-2 reach.
* **Win:** the text arm's interval is above the best image arm's at the same or higher chars per position, with
  equal or fewer training samples. Expected from the literature: near-lossless at r = 8 (~35 chars per slot),
  usable at r = 16.
* **Then the real bar:** needles and chains from the slots (`longctx_bench.py`). Published compressors all lose
  factual recall against full context (at ~9x: vision -2.23, text encoder -2.08, full context -1.07 answer
  log-likelihood), so a reconstruction win is not yet a usable-context win.
* **Cost:** ~2 h per ratio at Stage 0's 8000 steps (0.93 s/step, 10 GB); up to a day per ratio if the ladder
  needs ~100M tokens to copy.
